## 01 // PROBLEM
A chat tutor teaches what you think to ask. An exam asks the rest. With an 847-page textbook, I have no way to tell from a chat what I never touched.

So the thing to build wasn't a better answer. It was a list of everything in the material, and a way to prove that the plan, the lessons and the checks cover that list.

## 02 // APPROACH
Everything hangs off one table, the coverage ledger:

1. **Read.** Each page is mined for concepts, definitions, formulas, examples and procedures. Every item keeps the quote it came from, so opening its source highlights the actual line.
2. **Plan.** The model proposes the lessons, and code rejects any plan that leaves an item out. Then it schedules the lessons up to the exam date.
3. **Teach.** One step at a time, with citations to the book, figures when words aren't enough, and a check after each step. A wrong answer gets a repair before the lesson moves on.
4. **Test and keep.** Practice sets and timed mock exams are marked point by point against a mark scheme, including photos of handwriting. What I miss becomes a flashcard on a spaced schedule.

The teaching loop and the knowledge graph build on ideas from [LearnHarness](https://github.com/amosblomqvist/learnharness) by amosblomqvist. No code is copied; the ledger, the coverage check and the rest are what I added.

## 03 // BUILD
The server is Hono on Node 24, the UI is Svelte 5, and the data is one SQLite file on my disk. Any model works through my own key, with an ordered fallback list when one is busy or out of quota, and a usage page that shows where every token went.

- **Windows app:** a per-user PowerShell install with no admin rights. It ships Node, opens in its own window, and installs updates from a feed after checking each download's SHA-256.
- **Backups:** one zip that leaves keys out and restores at the next start.
- **Releases:** every push to main is meant to run the tests, package the app and publish a GitHub release. The workflow is written, and the first push will be its first real test.
- **The film on this page:** it's the real app running in iframes on an HTML stage, where every frame is a function of time, captured over the Chrome DevTools Protocol and piped to ffmpeg. The narration timings drive the subtitles and the cuts, and the music is synthesised in NumPy on the same beat grid.

## 04 // LEARNED
The hardest bugs only showed up on a real textbook:
- PDF text and what a model quotes back differ in ways that don't change the words: ligatures, words hyphenated across a line break, curly quotes. Matching only on case and spacing found 92.2 % of quotes. Normalising both sides and keeping each character's original offset took it to 96.7 %. The rest are rewritten maths and paraphrases, and those items link to the start of their section instead.
- The same pass cut repeated titles from 28 to 1 and merged items from 997 down to 944. The film was shot before that merge, which is why it says 996.
- Opening a source in a long PDF landed on the wrong place. Sections above it render lazily with `content-visibility`, so they change height after the scroll has finished. It now settles on the quote over a few frames.
- The Windows install broke on paths over 260 characters inside a dependency. Copying with robocopy and pruning files the app never loads fixed it.

What isn't proven yet: only Google AI Studio has been tested on a real model, and the other providers only against fakes. Handwriting marking has run through its code path, but not yet on a real photo with a real model.
